# Security implementation and boundaries

No credentials are in source, infrastructure parameters, images, or browser bundles. `.env`, SQLite data, test databases, locally edited deployment parameters, tool downloads and release artifacts are ignored. CI has read-only repository permissions, no AWS secrets/OIDC, no publication and no deployment.

Passwords use random-salted scrypt and constant-time digest comparison. Signup requires 12–128 characters including uppercase/lowercase/numbers and always assigns `user`. Organizer creation is restricted to the trusted local CLI; the HTTP API cannot choose role or organizer identity. Sessions use 32 random bytes, store only token hashes, expire after eight hours, and are revoked on logout. Tokens are in HttpOnly/SameSite=Lax cookies with Secure enabled for HTTPS production. Explicit SQLite classroom HTTP opt-in omits Secure because browsers cannot send Secure cookies over ordinary public HTTP. Stored user hashes never appear in public responses.

Mutating routes require an explicitly allowed Origin, including unauthenticated login/register/logout. Production requires the exact configured origin; development with a configured HTTP loopback origin additionally allows loopback host aliases on the known backend/Vite/configured ports. Neither Host nor Forwarded determines the allowlist; browsers send this for same-origin form fetches. There is no permissive CORS. Untrusted and missing origins remain rejected, preventing cookie-authenticated cross-site writes. HTTPS is required by default in production; SQLite classroom demonstrations can explicitly set `ALLOW_INSECURE_HTTP=true`, using disposable data and credentials only. That HTTP exception also removes HSTS and asset upgrade directives, and does not protect transport confidentiality. For the existing DynamoDB architecture, the cloud template redirects HTTP and requires an existing certificate. ALB terminates TLS; backend traffic is restricted VPC HTTP, not end-to-end encryption.

The backend authenticates all data API routes, validates strict schemas/UUIDs/date ranges/capacity/options and checks role/ownership. Names/details render as React text, not raw HTML. CSV quotes and formula-prefix escaping protect exported attendee names. Attendee identities are owner-only, other booking identities are redacted, and activities are scoped to the current user or resources they own. Poll results are intentionally visible to all signed-in users.

Helmet, a 32 KB JSON-body limit, request limits, generic internal errors and structured body-free logs provide a baseline. Per-process rate-limit counters are intentionally not shared; distributed abuse controls are needed before wider exposure. Readiness emits dependency status but no secrets. The DynamoDB deployment trusts one reverse-proxy hop and requires ALB-only network access. The SQLite deployment trusts loopback proxies and binds Node to 127.0.0.1 behind Nginx, which overwrites client forwarding headers.

AWS defaults off. `readConfig` rejects DynamoDB mode without a local HTTP endpoint or explicit `ALLOW_AWS=true`; local DynamoDB receives dummy credentials directly, with no account/metadata lookup. Production supports persistent file-backed SQLite for a single instance and preserves the optional shared DynamoDB mode. In-memory production SQLite is rejected; HTTPS origin is the default. The cloud instance uses an existing instance role, IMDSv2, encrypted disks/table, no SSH/public IPs, a table-scoped endpoint policy and database-backed sessions. This task did not connect to AWS to validate those controls.

This is a trusted classroom midpoint prototype. Before broad production use, add password reset/email verification, provisioning/role audit procedures, brute-force controls shared across instances, dependency update policy, organization/workspace isolation, backup/recovery exercises, registration cancellation policy for past events, monitoring/incident procedures and a measured security review. No password reset or account deletion button is presented as working.
