# Multi-workspace deployment handoff

## Application and storage changes

- `backend/src/workspaces.ts`, `workspace-routes.ts`, `workspace-store.ts`, and `resource-permissions.ts` implement workspace admission and policy. `app.ts` resolves every operational request against an authenticated membership and the requested workspace. Existing event, poll, slot and export URLs accept `X-Workspace-Id`. Browser CSV links select the workspace with the `workspace` query value.
- `workspace-migration.ts` and `scripts/migrate-workspaces.ts` add metadata to the existing versioned records table. The original Project workspace keeps the existing keys, IDs, ownership, summaries, event and schedule structures, and participation records. A new workspace uses `ws:<workspace-id>:<kind>` partitions and a transactional summary. Global appointment guards still prevent overlapping appointments across workspaces. Password hashes, account roles, guests and existing session records stay intact.
- The migration creates one Project workspace with an explicitly selected existing organizer as owner, enrolls existing organizers and administrators as managers there, and enrolls other existing accounts and guests as attendees there. New accounts and guests join by invitation. Owners can add a specific existing organizer as a manager. Invitations never grant management privileges.
- Invitations use a per-workspace random nonce and keyed derivation. The lookup stores a digest. Code display is limited to workspace owners and managers. Confirmation is signed, expires in ten minutes, and is checked again at admission. Failed invitations are rate-limited in shared storage. Keep the PostgreSQL backup and derived code data private.
- Archive pauses mutations and retains readable history for members. Owner-confirmed deletion requires an archive and an exact name. It marks the workspace deleted, revokes access, and retains its records for recovery. The original Project workspace is protected from deletion. The legacy destructive guest cleanup command is disabled after migration. Use membership removal for access revocation.
- `frontend/App.tsx`, `WorkspaceControls.tsx`, `workspace-api.ts`, `Modal.tsx`, `Groups.tsx`, `Polls.tsx`, `PollForm.tsx`, `Scheduling.tsx`, `api.ts`, and `styles.css` implement the scoped interface. The device remembers the selected workspace by identity. A refresh revalidates that selection. Poll deletion removes the poll aggregate, votes and results in a version-checked transaction with the summary and a minimal audit entry.
- `store.ts` and `postgres-store.ts` support transaction checks and version-conditional deletion. SQLite and PostgreSQL have the explicit migration command. Legacy DynamoDB remains available in single-workspace mode. No DynamoDB workspace migration is included.

## Dry run and migration

With both old writers stopped, use the release's CLI from an authorized private management environment. Set PostgreSQL connection and certificate settings through the established private mechanism. Use the authorized migration identity with table lock and insert permissions. Keep TLS verification enabled. Decide who owns the original Project workspace and use that existing organizer's email in the command.

```bash
# POSTGRES_URL and POSTGRES_CA_FILE must come from the private operator environment.
export DATABASE_DRIVER=postgres POSTGRES_SSL=verify-full ALLOW_AWS=true
node dist/backend/scripts/migrate-workspaces.js "$PROJECT_OWNER_EMAIL"
ALLOW_WORKSPACE_MIGRATION=true node dist/backend/scripts/migrate-workspaces.js "$PROJECT_OWNER_EMAIL" --apply
node dist/backend/scripts/migrate-workspaces.js "$PROJECT_OWNER_EMAIL"
```

The first command is a read-only transaction. Review counts, configured owner eligibility, and relationship validation before applying. The apply transaction locks the record table against concurrent writers and writes the marker, Project workspace, invitation digest, and paired memberships together. Exit on any validation failure. The last command must report `alreadyMigrated: true` and zero added records. Compare the original account, session and resource data and versions to the preflight counts and checks from the backup. In particular verify ten permanent accounts if that is the live preflight count, Alex Morgan's resource IDs and ownership, the nine groups of four, existing schedules, and the saved demo polls. Schema version remains PostgreSQL version 1 with a workspace data marker. Application startup does not perform this migration. The SQLite CLI uses the same dry-run/apply steps with a persistent local `SQLITE_PATH` and without PostgreSQL settings.

## Recovery

If migration validation fails, its transaction leaves the original rows unchanged. Keep old writers stopped while deciding whether to correct source data or abandon the cutover. If the application fails before traffic resumes, keep traffic closed, preserve the failed state for analysis, and either fix forward or use the verified pre-migration backup and the recorded prior release under the approved recovery process. After new writes have occurred, a pre-migration restore would discard them. Preserve a fresh backup and reconcile those changes before any restore. Serving the previous binary against the migrated live database would bypass workspace enforcement.

## Performance verification

Local PostgreSQL 17.12 was exercised with the existing integration runner. The separate loopback load runner (`POSTGRES_TEST_URL=<local-admin-url> node scripts/workspace-load.mjs` after `npm run build`) starts two independent Node processes and creates and drops one random disposable database. It permits loopback PostgreSQL only. The final 50-guest run had 659 requests, zero unexpected errors, 99 expected capacity conflicts, 50 expected forbidden deletions, and p50/p95/p99 of 25/590/1441 ms.
