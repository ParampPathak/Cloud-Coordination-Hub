# Plan B preparation and deployment gates

Prepared November 13, 2026 (America/Chicago). **Application/storage implementation and local verification are prepared; AWS infrastructure is not deployed.** No billable resources, IAM changes, production data edits or presentation edits were performed.

## Migration scope and implementation

The existing application stores versioned JSON aggregates through Store, rather than embedding SQL in feature handlers. Therefore the migration is a new storage adapter and operational path, not a rewrite of registration/booking rules. The SQLite and DynamoDB adapters and existing deployment templates are preserved. SQLite remains the local default and the Plan C feature fallback.

PostgresStore uses a pg connection pool (five connections per process by default), a cch.records JSONB table keyed by kind/id with C collation, a transactionally updated cch.summary row and an explicit schema-version marker. This preserves embedded registrations/groups/poll entries, scheduling guard records, password hashes, hashed session keys, expiry values and actor/organizer activity partitions. No application business-rule or frontend rewrite was needed.

Each transaction runs on one checked-out connection. Ordered row locks plus expected-version conditions protect all writes, activity indexes and summary deltas in a single BEGIN/COMMIT. A stale condition rolls everything back. Duplicate creation returns false; only serialization/deadlock/lock conflicts are retriable. SQL permission, schema, validation and connection failures propagate instead of being disguised as successful writes. No per-process queue is relied on for cross-instance correctness. Aggregate/document bounds from the existing implementation remain.

Reads use the primary-key index, bounded keyset pagination and one lookahead row; full list is retained for explicit maintenance/legacy compatibility. Indexed session cleanup deletes at most 500 expired entries per batch. Authentication checks expiry independently of cleanup. Production PostgreSQL requires a CA file, certificate/hostname verification and no URL query options that could override pg TLS settings. Remote access requires explicit ALLOW_AWS=true; local test/load paths continue to forbid AWS targets.

Schema initialization is an explicit owner operation, not server startup DDL. The runtime SQL role has schema USAGE, records/summary CRUD and read-only schema-version access, without schema ownership or CREATE privileges. init-postgres.ts serializes initializers with an advisory lock; normal application transactions do not take that lock. provision-postgres.ts creates cch_app without silently resetting an existing role. Neither command was run against AWS.

## Exact proposed AWS topology

CloudFront default managed HTTPS hostname -> IPv4 VPC origin -> internal ALB port 80 -> private app ASG, min/desired/max 2/2/3 across two supported AZs -> private Single-AZ RDS PostgreSQL 17.7 db.t3.micro with 20-GiB encrypted gp2. App roots are encrypted 30-GiB gp2, t3.micro with standard CPU credits, IMDSv2, no public IPv4 or SSH. A VPC internet gateway is attached for CloudFront's prerequisite but there are no public/default subnet routes or NAT gateways. A regional S3 gateway endpoint supplies Amazon Linux packages and reviewed release/config objects.

PostgreSQL TLS is required by both the database parameter group and the application. Browser TLS terminates at CloudFront; the ALB/application hops use private HTTP. API/private/error caching is disabled, all cookies and query parameters are forwarded, and Origin is forwarded with other viewer headers except Host. Sticky sessions are disabled; sessions persist in PostgreSQL. The default CloudFront certificate must not be described as a custom-domain certificate or a verified minimum viewer TLS 1.2 policy.

Database ingress is only from the application security group. An approved CloudShell VPC management environment can later use that group to perform private owner setup; no public DB or public management instance is proposed. Its actual connectivity is unverified. The owner password remains private to the operator and the NoEcho CloudFormation parameter; it is never placed in app UserData, S3 app configuration, Git or the application image. The runtime JSON contains only cch_app's URL and the public RDS CA bundle. Keep it in private encrypted same-region S3, block public access, and never put the owner credential under any prefix readable by app instances. The existing myS3Role is broad S3 access, so do not pretend that role is project-scoped. The endpoint policy limits the app network path to release/config reads, log writes and regional package reads.

Native CloudWatch metrics and three alarms cover unhealthy ALB targets, RDS CPU and free storage. Bounded application log batches go to private S3 every five minutes; upload failures remain visible in the timer unit and do not stop application service. Overlapping batches may contain duplicates. Direct CloudWatch application logs/memory metrics and the optional Lambda forwarder are not implemented in this baseline. This is a monitoring difference from the full poster architecture.

## Bootstrap and release inputs

The bootstrap is prepared as a separate, checksummed S3 object. UserData first fetches it with the existing EC2 S3 identity and verifies SHA-256; it contains no SQL password. The script installs an exact Docker RPM from the pinned Amazon-owned AL2023 release via regional S3, verifies and loads the offline application image, reads private app-only JSON, creates a root-only Docker env file and starts a hardened non-root container under systemd. The RDS CA is mounted read-only. Application restarts are automatic; initial bootstrap failure is not hidden by an ASG success signal.

Before provisioning, produce a new clean-checkout Docker release with scripts/prepare-plan-b-release.sh in a Docker-capable local or free build environment. This script does not upload or call AWS. It requires a clean commit, checks that pg and all maintenance entry points are packaged, preserves an existing output directory, and emits the image tar, checksums, release metadata, compressed archive and separate bootstrap checksum. Resolve and record the exact Docker RPM version against the chosen AMI release; this required parameter deliberately has no floating default. Record the AMI owner, root-device size, Node/container versions, final commit and artifact SHA-256. Do not reuse the old SQLite-only image or bake credentials/data into a new image.

The standard AL2023 S3 repository path was confirmed from CloudShell's repository configuration, with RPM signature checking enabled. The actual app-node install through the new endpoint has not been executed. The endpoint allows the regional al2023-repos-us-east-1-de612dc2 bucket; do not switch to cdn.amazonlinux.com or disable GPG checks when private routing fails. Stage the public [regional RDS CA bundle](https://truststore.pki.rds.amazonaws.com/us-east-1/us-east-1-bundle.pem) through the reviewed configuration process, since private app nodes cannot fetch arbitrary internet URLs.

The NoEcho database password parameter intentionally triggers cfn-lint W1011's preference for secret-manager dynamic references. Use a private mode-0600 parameter file/secure input, not a literal command-line secret, and never expose resolved values in outputs or logs. Other schema checks remain enabled.

## Migration and rollback

For existing SQLite data, stop all writers, make a private verified backup, then use data:migrate export SOURCE.sqlite UNUSED_BACKUP.json. Existing backup paths are never overwritten. Against the initialized PostgreSQL target, import defaults to comparison; apply requires both ALLOW_DATA_IMPORT=true and --apply. Existing differing records cause an abort. Conditional batches, post-import comparison and retry-safe identical records permit resume. The whole import is not one transaction; keep writers stopped until every source record is verified. The source file and JSON remain unchanged. Imports may include password hashes and student data, so keep them out of Git and presentation artifacts.

For a new demo, create fresh controlled organizer and attendee accounts using the trusted CLI after DB readiness. Generate unique random passwords, save them in local ignored credentials artifacts and do not send them in chat. Do not seed arbitrary cloud sample accounts. Rollback to SQLite requires preserving the original stopped-writer SQLite source; changes made after cutover require a separate reviewed export/reconciliation, not a blind old-file restore. PostgreSQL backups use pg_dump/restore or RDS snapshots under explicit backup/restore approval; no actual backup/restore was performed. Snapshot retention is not protection from an Academy account reset: export a verified private backup outside the Sandbox.
