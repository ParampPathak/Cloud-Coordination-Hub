# AWS deployment alternatives - evidence-based review

Reviewed 13 November 2026, America/Chicago. Region: us-east-1. This was a read-only investigation: no IAM edits, role assumptions, billable provisioning, application-data changes, or presentation edits. EC2 launch checks used DryRun=True exclusively. Main and all existing deployment work were preserved.

**Recommendation: Plan B is the strongest permission-feasible alternative if PostgreSQL is an acceptable substitution for DynamoDB. Plan C is the lowest implementation-risk route to a feature demonstration. The exact DynamoDB design in Plan A remains blocked with the identities currently available.** These are prospective plans, not verified running deployments.

**Later preparation update:** the PostgreSQL adapter and separate Plan B template are now implemented and locally tested. Read [Plan B preparation and new lifecycle blockers](plan-b-preparation.md). The audit below records the earlier decision point; its statements that no adapter existed are historical, and none of its permission checks establishes deployment.

## What AWS currently permits

No project EC2 instances, ALBs, ASGs, DynamoDB tables, RDS databases, cache clusters, Lambda functions, ECS clusters, S3 buckets, owned AMIs, distributions, certificates or hosted zones were found. Preserve the default VPC and Academy-managed stack.

The following operator actions simulated allowed with no missing context: VPC/subnet/routes/Internet Gateway/security-group/endpoint/launch-template creation; ALB/target-group/listener creation and registration; ASG creation/scaling policy; CloudFormation stack/change-set creation; S3 bucket creation; RDS instance/subnet-group creation; CloudFront distribution/VPC-origin creation; Lambda function creation/invocation/resource invocation permission; S3 notifications; and CloudWatch groups/dashboards/alarms. A specific RDS PostgreSQL db.t3.micro, 20-GiB proposal also simulated allowed. These results do not prove future capacity, bootstrap, service quotas, network connectivity, or successful deployment.

VPC, ALB and ASG can be prepared independently of the missing DynamoDB application role. An ASG can have no instance profile or use an approved existing one. A network scaffold with ASG min/desired zero would not provide two running healthy application instances. An empty ALB still charges; there is little benefit in provisioning an idle scaffold before its application path is ready.

**A custom AMI and a paid builder are unnecessary for a supported bootstrap design.** Prefer the standard AL2023 AMI: it has AWS CLI v2, and AWS documents package installation from private subnets through an S3 gateway endpoint. Allow the regional Amazon Linux repository bucket plus project artifact/config/log prefixes in that endpoint policy. No NAT, registry pull, GitHub clone, Console key injection, or public SSH is required on the app nodes. An ECS-optimized image is another candidate; its minimal base must not be assumed to include AWS CLI, so its downloader/package prerequisites need explicit validation.

It contains the application image, not production data or credentials. Deployment templates must use /dev/xvda and the selected image's minimum root size, rather than blindly reusing the Ubuntu-oriented /dev/sda1 and 12-GiB assumptions.

### CloudWatch without changing the EC2 role

EC2, ALB, ASG and RDS native metrics do not require the app to call PutMetricData. myS3Role can upload sanitized application log batches to private S3. Baseline Plan B can retain those logs in S3 and use native CloudWatch dashboards/alarms, with application logs/memory absent from CloudWatch.

An optional enhancement can use lambda-run-role for its intended Lambda/S3/log-processing purpose: S3 log batches trigger a Lambda that reads them and writes original JSON messages to the app log group. No role policy changes or direct EC2 log permission are needed. The current operator's Lambda creation, PassRole-to-Lambda, S3 notification and Lambda AddPermission checks passed. The S3 trigger requires a new, tightly scoped Lambda resource-based invocation policy; this must be included in explicit deployment/access approval. If the requirement forbids all new resource-policy grants as well as new role permissions, omit this enhancement. It is asynchronous, has possible duplicate events, and must be tested before claiming complete monitoring or accurate diagnostic counts. Restrict the trigger to a log prefix so its own outputs cannot retrigger it. Do not use it as a DynamoDB proxy.

Source: [S3 notifications and Lambda permissions](https://docs.aws.amazon.com/lambda/latest/dg/with-s3.html).

## Plan A - full required architecture

**Exact architecture:** Browser HTTPS -> public ALB 443, HTTP 80 redirect -> ASG min/desired/max 2/2/3 in two private AZ subnets -> shared DynamoDB via gateway endpoint. CloudWatch receives app logs/host samples through its private endpoint, plus native metrics/dashboard/six alarms. Dedicated 10.42.0.0/16 VPC, two public and two private subnets, IGW, secure SGs, no NAT. A separately approved domain-free variant inserts CloudFront HTTPS and moves the ALB to private HTTP ingress.

**Required permissions:** existing network/EC2/ELB/ASG/CloudFormation/CloudWatch control-plane actions; EC2-trusted application identity with the five scoped DynamoDB actions, log-stream delivery and authorized PassRole; matching ACM/DNS for exact ingress, or already-permitted CloudFront/VPC-origin/service-linked-role actions for the variant. S3 bootstrap also needs artifact GetObject; the currently requested admin policy must be revised if this bootstrap is chosen.

**Currently possible:** network/ALB/ASG scaffolding, production image preparation, Amazon-owned/S3 private bootstrap and native monitoring definitions.

**Blocked:** no usable approved DynamoDB compute identity; actual EMR PassRole failure; no matching certificate/DNS for the exact ALB ingress. These are independent of the custom AMI issue, which has a supported alternative. No healthy final targets, accounts or live tests exist.

**Poster difference:** none if exact ingress/access is supplied; CloudFront variant changes TLS termination and ALB placement. **Repository changes:** preserve hub.yaml/hub-cloudfront.json; add S3 bootstrap/endpoint and image-root parameters, review the actual approved profile permissions, stage credentials/accounts securely, add live test guards/evidence. Do not edit the poster or presentation.

**Estimated 3-hour reserve:** $2 for the CloudFront variant, subject to updated review and actual usage. This plan is not currently executable in full with the approved identities.

## Plan B - strongest alternative using existing role permissions

**Exact architecture:** Browser -> CloudFront managed HTTPS -> private internal ALB -> ASG 2/2/3 across two private app AZs -> private Single-AZ RDS PostgreSQL db.t3.micro, 20-GiB gp2. Use standard Amazon AL2023, private S3 package/artifact/config access via gateway endpoint, and the existing myS3Role profile. Require verified PostgreSQL TLS and a restricted SQL app account. Use native CloudWatch EC2/ALB/ASG/RDS metrics and S3 app logs; optional approved S3-to-Lambda log forwarding uses existing lambda-run-role and a scoped function invocation policy.

**Required permissions:** existing EC2 PassRole to myS3Role, network/ALB/ASG/CloudFront and RDS control-plane permissions, S3 reads/writes for artifacts/config/logs. Optional log forwarding additionally uses the already-allowed PassRole to lambda-run-role, Lambda creation and S3 notification/resource invocation policy actions. No IAM database authentication or DynamoDB grant is needed. Approval to use the existing lab roles for this project is still required; no unrelated EMR/platform role is used.

**Currently possible:** the permission evidence supports this design, including a specific PostgreSQL creation simulation, current orderable gp2 options, accepted EC2/S3 DryRun and existing RDS/ASG/ELB service-linked roles.

**Blocked/unimplemented:** no PostgreSQL Store adapter exists. backend/src/config.ts currently accepts only SQLite/DynamoDB and explicitly requires DynamoDB for aws-multi; backend/src/store.ts supplies only those two stores. A PostgreSQL adapter must preserve atomic multi-record version checks, summary counters, per-user activity, pagination, session expiry and concurrent booking invariants. New driver/config/metadata, SQL initialization/migration/backup, controlled credential delivery and regression/concurrency tests are necessary. Runtime capacity, private bootstrap and 50-user performance remain unproved. These are implementation/verification tasks, not a demonstrated need for new app-role permissions.

**Poster difference:** RDS replaces DynamoDB; app nodes are multi-AZ but the DB is a Single-AZ failure point; CloudFront changes ingress/TLS termination and ALB placement; baseline app logs remain in S3 unless the optional forwarder is approved. Do not label this as the required managed-DynamoDB architecture or end-to-end multi-AZ database availability.

**Repository changes:** implement/test the PostgreSQL Store and its migration/export path; extend configuration/deployment metadata truthfully; derive a separately named RDS CloudFormation variant, preserving original templates; add S3 bootstrap/private management/log shipping and optional forwarder; test all features, persistence, 50 users and controlled one-app failure after approval. Do not weaken the existing local-only load runner or production endpoint guards.

**Estimated 3-hour reserve:** $3, including burst-credit/extra-node headroom. This is the strongest architecture the current permission evidence supports if the database substitution is acceptable.

## Plan C - reliable feature demonstration fallback

**Exact architecture:** Browser -> CloudFront managed HTTPS -> direct private EC2 VPC origin, one t3.micro running the existing Node 24/React/Express release -> SQLite on an encrypted retained EBS-backed host directory. Existing myS3Role handles S3 bootstrap, log batches and verified backups. No ALB, app ASG, DynamoDB or RDS. No public app IP/SSH/NAT. Use the Amazon-owned standard AL2023 image and regional S3 package/artifact path.

**Required permissions:** the accepted EC2/myS3Role PassRole path, VPC/subnet/SG/S3 endpoint and artifact permissions, CloudFront/VPC-origin actions and its already-permitted service-linked-role creation. No application DynamoDB or direct CloudWatch Logs permission is needed.

**Currently possible:** existing SQLite feature code, trusted account-provisioning CLI and verified production image are ready. Two image/profile DryRuns support the compute path. This can be recreated from the preserved release without recovering an old custom AMI.

**Blocked/unimplemented:** no direct-EC2 CloudFront recovery template/bootstrap exists yet. The existing offline Docker installer does not mount persistent /app/data; adapt it to a real EBS-backed bind mount, correct ownership and secure runtime env. The direct EC2 origin creates an APP_ORIGIN dependency cycle if its UserData references the distribution that needs that instance: use a reproducible two-phase workflow that writes the known hostname to private S3 runtime config after CloudFront creation, while the service waits safely for that exact config. Do not infer trusted Origin from arbitrary requests. Build private SQLite-consistent backup/restore; copying only a live WAL database file is not a backup.

**Reliability:** systemd restarts the container; stop/start can retain EBS data; verify restore from a private backup copied outside the Sandbox. One node is a single point of failure and has no scale-out guarantee. Replacements cannot be assumed to preserve its local database. Provision fresh organizer/attendee accounts with random passwords through the trusted CLI, save credentials locally outside Git, and test every feature before screenshots. No such final fallback accounts or 50-user AWS result exist yet.

**Poster difference:** single node/local SQLite, no ALB/ASG/shared DynamoDB, reduced observability and no multi-AZ availability. **Repository changes:** add separately named fallback template/AL2023 bootstrap, persistent data mount, staged exact-origin config, backup/recovery and secure account-provisioning procedure. Business feature/storage logic can remain the tested SQLite implementation.

**Estimated 3-hour reserve:** $1. This is the fastest, lowest application-change route to a classroom demonstration, after deployment and verification.
